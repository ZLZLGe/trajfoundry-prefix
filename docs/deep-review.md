# 已去重结果的深度排查

`scripts/deep_review.py` 是只读 Cluster 诊断入口。它读取最终保留清单，核验每个文件的字节数和 SHA256，生成紧凑消息索引。它不输出新轨迹、不改正式去重规则、不写 S3。

诊断策略固定为现有五条消息规则和 `messages_only`。首先仍应使用普通比较入口，对完整保留集再跑一次 `--check-only`，确认现有规则下是否还有可覆盖记录。

| 索引模式 | 寻找的问题 | 门槛 |
| --- | --- | --- |
| current | 现有规则下仍有完整消息覆盖 | 至少 2 条比较消息 |
| format | CRLF、消息末尾空白、工具参数 JSON 编码及其组合 | 至少 2 条比较消息 |
| without_headers | 开头连续 system/developer 不同，但后续形成完整前缀 | 至少 4 条剩余消息 |
| without_notifications | user 中以 `<task-notification>` 开头的通知插入或省略 | 至少 4 条剩余消息 |
| without_headers_and_notifications | 开头指令与通知的组合差异 | 至少 4 条剩余消息 |
| format_without_headers_and_notifications | 格式、开头指令、通知组合 | 至少 4 条剩余消息 |
| cross_identity | 消息覆盖被用户、end-user、session 身份边界隔开 | 至少 6 条消息、有工具结果、内容字符总数至少 1,024 |

除跨身份诊断外，各模式仍使用原来的全部身份分组。跨身份诊断仍限同渠道、实际模型、harness 和日期，且记录被跨越的具体身份字段。身份脱敏、工具绑定异常等已隔离的轨迹参与输入数量和原因统计，但不会进入可覆盖候选比较。

所有符合门槛的记录都进入对应模式的前缀排序，不抽样。索引中的哈希仅用来找候选；每条完整覆盖候选都重新读取两份完整原始 JSON，逐条比较实际变换后的消息，并用独立的 `raw_covers` 检查原正式规则是否也能覆盖。报告中候选可以跨模式重复，不能相加，也不能把这些变换当作删除授权。忽略真实指令、通知或身份可能丢失信息。

同组排序相邻、至少 6 条消息、共同前缀至少 4 条且覆盖较短序列至少 50% 的记录，另记为近似前缀候选。如果首次分歧含已知脱敏占位符，共同前缀门槛降低到 2 条；这能找到中途 UUID、数字等脱敏差异较早出现的情况。所有首次分歧含占位符的候选对，都会重新读取完整原文、核对整个短序列，记录占位符是否足以解释全部差异。候选总量及跨模式去重后的配对数写入 `mask-counts.json`，逐对检查写入 `mask-candidate-checks/`。

具体差异展示按每个渠道、模式、关系或首次分歧角色组合固定选最多 5 对，再补充每个渠道和模式最多 5 对完整消息满足占位符匹配的例子。这些样例不用于估计全量脱敏问题比例。近邻检查不是全量两两比较，也不覆盖前两条消息就出现脱敏分歧的所有情况。占位符能解释当前字符串差异，并不证明原始值一定相同，仍须追溯原始请求。

占位符诊断采用可达字符位置区间计算，保持每个占位符匹配 1–256 个非 CR/LF 字符的原口径。重复占位符遇到后段真实差异时，不再发生正则的指数级回溯；这仅修复诊断性能，不改变正式去重规则或候选匹配含义。

主要产物：`inventory.json` 为全量读取与各模式资格统计；`candidate-counts.json` 为候选计数；`verified-candidates/` 为每条完整覆盖候选的实值核验；`sample-evidence/` 为有限具体差异；`report.json` 汇总数量与范围限制。轨迹引用和摘录仅在仓库外的共享运行目录保存。

该入口必须由 `spark-submit --deploy-mode cluster` 提交，不能在本地 Python 或 local Spark 中处理业务数据。运行参数要求明确指定保留清单的预期数量和 SHA256；开始和结束均复核清单哈希。
