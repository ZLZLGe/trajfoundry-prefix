## 已验证的鲁棒问题

所有修正规则只用于比较，不修改保留轨迹的任何字段或原始字节。每条合并记录必须有最终保留的完整轨迹作为覆盖依据。

| 问题 | 为什么需要处理 | 边界 |
|---|---|---|
| Claude billing header 的动态 `cch` | 原始响应在后续请求回放时，此计费标记变化会阻断相同历史 | 仅处理 system/developer 开头指定 header 中的十六进制值；其他系统指令仍比较 |
| assistant 末尾 ASCII 空白 | 相同工具调用在 response 和下次 request 中可能只差末尾换行 | 只去比较副本末尾空格、tab、CR、LF，正文内部、其他角色和 Unicode 空白不变 |
| tool call ID 一致更名 | 原始采集已出现 `chatcmpl-tool-…` 到 `call_…`，原标准化保留不同 ID | 维护一一对应的调用／结果绑定；工具名、参数、顺序和结果仍须一致 |
| 回放省略全空 assistant | 大样本保留结果中发现，正常交互之后的全空回复在后续历史中消失 | 不跳过起始空回复、仅推理回复、未知扩展或任何含工具／媒体的消息 |

第四条来自首轮真实残余分析：对 242 对疑似空消息回放进行独立核对，确认 241 对，另 1 对因空回复位于正常 assistant 交互之前而排除。同一批 617,853 条输入增加这一条规则，实际多合并 **306 条**。候选对数与全量新增合并条数不是同一种统计。

按用户确认的分类用途，额外信息只约束 **工具定义完整包含**；子 agent、压缩项、媒体映射、服务端调用附录、来源扩展、顶层 instructions 等不阻断合并。消息内的 system/developer 指令、正文、工具参数与结果仍比较。

|---|---:|---:|---:|
| 前三条规则，保留全部额外信息约束 | 592,156 | 25,697 | — |
| 四条规则，保留全部额外信息约束 | 591,850 | 26,003 | 306 |

## 覆盖范围

Boyue、DeepInfra、FreeRouter、TokenPlan 各选 10 个不同日期，具体是“跨时间选日期，再在日期内抽样”：

1. 从冻结的标准化 inventory 筛选当天条数至少 5,000 的日期，按日期升序排列。符合条件的日期数分别为 237、90、56、47。
2. 在上述列表中取 `round(i × (N−1) / 9)`，其中 `i=0…9`，覆盖列表首尾。这是按可用日期列表的位置等间隔选取，不是按自然日间隔或当天数据量加权抽取。
3. TokenPlan 原选中的 2026-09-29 替换为 2026-09-30，并在该日强制纳入此前核查的 58 个文件名家族，用于已知问题回归。
4. 每天以 12,000 条为期望目标。先去掉文件名末尾 `_sub_N` 得到家族名，对 `渠道|prefix-20261117|家族名` 求固定 SHA256；采样概率为 `min(1, 12000 / 当天条数)`。某个家族一旦选中，该日期里属于它的所有分支都纳入；当天不超过 12,000 条时全量纳入。

12,000 是期望数量，不是截断上限。一个很大的家族是否被选中，会导致实际条数明显波动，例如 FreeRouter 有一天选了 18,496 条，也有一天只有 3,973 条。此选择用于覆盖时间段、验证完整分支关系和发现问题，不是估计全历史重复率的随机抽样设计。

SXF 当前清单只有 2026-08-21，测试全部 108,531 条；TrustCyberData 三套都是一次性归档，分别测试全部 19,398、18,783、401 条，没有人为虚构十个日期。

无 session 的文件名家族不等同于完整隐含会话；稀疏样本可能没有同时抽中可互相覆盖的两个文件。这会影响对全量可合并比例的估计。

## 分组与大分支编号

仍按渠道／数据集、model、harness、用户身份分组。有真实 session 时再按 session；没有 session 时按日期。`sub_session_id`、`sessionless_chunk_id` 和 `_sub_N` 不会拆开比较组。哈希只用于候选排序和分区，最终删除需要真实比较内容完全覆盖。

对完整大编号家族的检查：TokenPlan 一个家族 **831 → 100**；SXF 一个家族 **604 → 569**。FreeRouter 的 `intern-discovery` 有 14,567 条，但首个 user 消息有 14,354 种，最终保留 14,567 条。因此大编号可能包含旧匹配遗漏，也可能来自复用 session 标识的不同问题，不能仅按编号合并。完整身份与日期、前后条数见 [分组说明](grouping.md)。

输出不重新编号；保留 `_sub_14566` 不代表输出仍有 14,567 条。总条数以输出 manifest 为准。

## 完整核验与残余检查

独立 Cluster 核验已成功：输入与决策完整对应；590,874 个实际输出文件的原始字节数和 SHA256 全部一致；26,979 条删除关系全部由独立的原始 JSON 比较器验证，并确认指向实际保留的最终文件。核验没有用输入缓存代替实际输出文件。

26,979 条最终对应关系中，11,803 条在关闭四条鲁棒规则后仍成立，15,176 条依赖至少一条鲁棒规则。逐项关闭规则得到以下互斥组合。这里解释的是本次最终删除关系，不能把它当作各规则单独运行后的全量收益；附加信息策略始终固定为 `tools_only`。

| 最终覆盖关系依赖的规则 | 条数 |
|---|---:|
| 无需四条鲁棒规则 | 11,803 |
| 仅工具 ID 更名 | 10,696 |
| 仅 billing cch | 2,959 |
| 仅 assistant 尾部空白 | 1,093 |
| 仅全空 assistant | 267 |
| billing cch + 尾部空白 | 70 |
| 尾部空白 + 工具 ID | 50 |
| 尾部空白 + 全空 assistant | 40 |
| 工具 ID + 全空 assistant | 1 |

把全部 590,874 条保留结果重新作为输入，第二遍 Cluster 实跑仍保留 590,874 条，**新增合并 0 条，观察比例为 0 / 590,874 = 0%**；各渠道条数和总输出字节均不变。这证明本次输入、分组及已定义规则下未留下可继续合并的记录，不代表所有可能的语义重复都为零。

另逐个读取了全部 590,874 条保留轨迹，在原排序分区内检查相邻同组记录。短轨迹至少 4 条消息、共同前缀至少达到短轨迹的 80% 时，计为一对近似前缀候选。共发现 **38,124 对**，首次分歧或保留原因如下：

| 首次分歧／保留原因 | 候选对数 |
|---|---:|
| assistant 工具调用不同 | 16,060 |
| assistant 正文不同 | 6,473 |
| assistant 正文和工具调用都不同 | 5,188 |
| user 正文不同 | 4,713 |
| 对应位置的消息角色不同 | 3,120 |
| 消息前缀覆盖，但工具定义或准入保护阻止合并 | 1,947 |
| 工具结果内容／绑定不同 | 562 |
| system／developer 正文不同 | 61 |

这 38,124 是候选对数，不是重复轨迹数，也不是还能删除 38,124 条。它们没有通过当前覆盖规则。检查保存了 17,738 对有界样例：其中 1,761 对为消息覆盖但受保护的情况，278 对缺工具定义，其余 1,483 对受身份／历史长度／工具绑定等准入条件保护。样例不是候选对的随机抽样，不能据此推断全部候选的子类比例。

对“assistant 工具调用不同”的样例又按固定哈希取 300 对，重新读取完整保留文件，检查首个不同位置：123 对调用数量不同，6 对工具名或顺序不同，171 对参数值或其他调用字段不同；没有发现仅解析 arguments JSON 后便相同的情况。这不支持把这一大类继续当作纯 ID／格式差异直接忽略。

仍保留的实际差异包括不同用户任务、工具参数或结果、非空 assistant 在回放中被省略、脱敏文本前后不一致、消息中的摘要或指令变化，以及工具定义缺失。单独存放的压缩信息已放宽；消息中真正出现的摘要或角色变化继续保留。相邻扫描还不能穷尽首两条消息不同等情况，因此不能宣称不存在其他待验证的归一化机会。

自动化测试共 **59 项通过**，包含工具引用错配、匿名范围、未知消息扩展、原字节保留、Spark 集成及新附加信息策略；静态检查通过。生产规模实测、全量核验和第二遍检查均走用户 Cluster 队列。
