## 已核实的具体原因

1. 同一 TokenPlan 会话的 `_sub_57`、`_sub_63` 与 `_sub_65`，比较消息数分别为 269→286、282→286；不同点仅在 tool.content 的 1、2 个位置。通过 lineage 定位三个采集请求，核验 masked-raw 哈希并对照脱敏前 raw，确认原值相同而部分 UUID 在不同快照中被不一致地替换为占位符。标准化内容等于对应 masked-raw 内容。这里完成的是字段溯源和标准化完整序列核验，没有声称重跑原始标准化流程。
2. 开头指令候选包含整段行为说明的追加；task-notification 候选包含后台任务结果、状态和工具引用。因此整段忽略只能作为诊断，不能据此直接删除。
3. 新发现的 8 对定向样例又在 Cluster 中重读核验：1 对去掉 assistant 尾部 DCP 标签后形成 62→88 条消息的完整前缀；4 对忽略 OpenClaw 标记的运行时上下文后形成完整前缀；1 对仅差 assistant 正文 XML 参数值前的空格，处理后形成 44→54 条消息的完整前缀。这三类尚未全量计数，也未加入正式删除规则。
4. 另外两对仍不满足这些探针：一对正文实际不同；一对工具参数为截断、未闭合的 JSON，另侧为完整解析对象，无损解包不能解释差异。共享开头不能直接等同于整条轨迹被覆盖。

`messages_only` 忽略顶层附加信息，仍保留身份分组，并比较 messages 内部正文和结构。因此 DCP/OpenClaw 等写入 messages 的内容仍会影响前缀。
